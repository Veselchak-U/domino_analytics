# Локальные фронтенд, бэкенд и SQLite в Docker Desktop

Запустите Docker Desktop в режиме Linux containers. Отдельная Ubuntu VM не нужна. Сайт доступен по [http://127.0.0.1:3210](http://127.0.0.1:3210).

## Бат-файлы в корне проекта

| Файл | Действие |
|---|---|
| [open-site.cmd](../../open-site.cmd) | Открыть сайт в браузере; сервисы должны быть уже запущены |
| [start-docker.cmd](../../start-docker.cmd) | Собрать при необходимости и запустить оба сервиса |
| [stop-docker.cmd](../../stop-docker.cmd) | Остановить сервисы, сохранив БД |
| [update-docker.cmd](../../update-docker.cmd) | Сделать backup работающей БД, пересобрать образы и обновить контейнеры |
| [restart-docker.cmd](../../restart-docker.cmd) | Перезапустить сервисы без пересборки |
| [status-docker.cmd](../../status-docker.cmd) | Показать состояние контейнеров |
| [logs-docker.cmd](../../logs-docker.cmd) | Показать последние сообщения обоих сервисов |
| [backup-docker.cmd](../../backup-docker.cmd) | Сделать согласованную резервную копию SQLite и выгрузить её в .analysis/backups |

Достаточно двойного щелчка. Файлы вызывают [manage-docker.ps1](../../manage-docker.ps1), работающий из любого текущего каталога и находящий также установку Docker Desktop для текущего пользователя. Для start/stop/update/restart терминал после успешного завершения можно закрыть. Status/logs/backup оставляют окно открытым для чтения результата. Ошибка также оставляет окно открытым.

В Docker Desktop группа называется `domino-local`, сервисы — `frontend` и `backend`. При переходе с прежней версии контейнер `app` заменяется этими двумя. Старая версия держала игры только в памяти: ранее загруженные в неё файлы нужно один раз импортировать заново. Новые импорты и готовые результаты уже постоянные.

## Как пользоваться

Загрузите JSON через интерфейс. Он проверяется до записи в БД, исходный текст не меняется. В списке «Сохранённые игры» появляются имя файла и готовность раундов. Повтор того же файла не создаёт дубль и сохраняет первое имя.

После обновления страницы или перезапуска Docker выберите игру из этого списка; последняя открытая игра также может восстановиться автоматически. Готовые раунды читаются из БД без полного перебора. Недостающие раунды рассчитываются последовательно, как раньше. Отмена не удаляет уже готовые результаты. Прерванный перезапуском раунд можно запустить снова.

## Команды PowerShell

Из корня проекта вместо бат-файлов можно выполнять:

```powershell
./manage-docker.ps1 -Action Start
./manage-docker.ps1 -Action Stop
./manage-docker.ps1 -Action Update
./manage-docker.ps1 -Action Restart
./manage-docker.ps1 -Action Status
./manage-docker.ps1 -Action Logs
./manage-docker.ps1 -Action Backup
```

Если политика PowerShell запрещает запуск, используйте `.cmd`-файлы; они задают политику только для своего процесса. Docker Desktop должен оставаться запущенным.

## Хранение и резервные копии

SQLite находится в `/data/domino.sqlite` на именованном томе **domino-local_backend_data**. Фронтенд не монтирует этот том, порт бэкенда не опубликован. Stop, restart, start и update том не удаляют. Не удаляйте этот том вручную и не используйте `docker compose down -v`, если хотите сохранить библиотеку.

Backup создаётся через SQLite `VACUUM INTO`, проверяется на целостность и копируется на компьютер в `.analysis/backups/domino-<дата-время>.sqlite`. Бэкенд должен работать. Это самостоятельный файл, включающий завершённые записи WAL; копировать один открытый исходный `.sqlite` без WAL вручную не нужно. Чтобы восстановить копию, остановите сервисы, сохраните прежний том и используйте проверенный файл как `DATABASE_PATH` в отдельной конфигурации; не заменяйте открытую БД.

Необязательные локальные примеры по-прежнему можно **скопировать** в `.analysis/docker-data/examples`; каталог подключается backend только для чтения. Игры, загруженные через браузер, хранятся в SQLite и не требуют размещения в этой папке. Исходные пользовательские JSON, БД и резервные копии не включаются в Docker-образы и не публикуются в registry.

## Разработка без Docker

Нужен Node.js 22.13+ и `npm ci`. `npm start` запускает frontend и backend с БД `.analysis/domino.sqlite`; при этом остановите Docker-контейнеры, чтобы освободить порт 3210. Для двух отдельных процессов есть `npm run start:backend` (по умолчанию 3211) и `npm run start:frontend` (3210). Backend принимает `DATABASE_PATH`, `PORT`, `HOST`, `DOMINO_ALLOWED_ORIGINS`; frontend — `BACKEND_URL`, `API_BASE_URL`, `PORT`, `HOST`.

После изменения исходников выполните update-docker.cmd: файлы приложения не смонтированы в контейнер, требуется пересборка. Полный перебор остаётся точным; при нехватке ресурсов результат не заменяется выборкой.

## Проверки

`npm test`, `npm run check` проверяют домино, хранение, HTTP и жизненный цикл. `node tools/docker-smoke.js seed` на клиентском компьютере считает тестовый раунд/ветвь/урок и загружает компактные результаты; после перезапуска или пересоздания контейнеров `node tools/docker-smoke.js verify` проверяет неизменность чисел и cached:true. Используются только тестовые данные репозитория и loopback.

Публичный доступ, парольный вход и облака в этот локальный этап не входят. Для будущего отдельного серверного стенда сохранена [инструкция VM](../vm/README.md).

## Клиентские вычисления и замена старой БД

Полная проверка, solver, ветки и уроки выполняются в браузере. Backend хранит только исходники и готовые компактные анализы; глобальной очереди расчётов нет. В Compose лимит backend снижен до 384 МиБ и 0,5 CPU; память браузера сюда не входит. Вычислительные Node-зависимости серверу при запуске не нужны.

Старая схема SQLite заменяется новой пустой БД без миграции: прежние партии, результаты и jobs удаляются. Пользовательские JSON на диске остаются неизменными. При последующих перезапусках актуальная схема и новые записи сохраняются. Для отката прежним релизом нужна отдельная БД его схемы; автоматического переноса нет.
