# Запуск на локальной виртуальной машине

Для повседневного запуска на Windows используйте [инструкцию Docker Desktop](../desktop/README.md). Отдельная VM нужна только как дополнительный серверный стенд.

Это совместимая прежняя одноконтейнерная поставка для серверного стенда: два HTTP-приложения запускаются внутри одного контейнера. Для текущей разработки используйте двухконтейнерную поставку Docker Desktop. Здесь SQLite хранится в data/domino.sqlite, готовые результаты и игры сохраняются при перезапуске. Публичная авторизация и облачное размещение не добавлены.

## 1. Локальная VM

Создайте в VirtualBox, Hyper-V, VMware или другом гипервизоре VM:

- Ubuntu Server **24.04 LTS, x86-64 / amd64**;
- 2 vCPU, 4 ГБ RAM, диск от 30 ГБ;
- OpenSSH Server и сеть, по которой компьютер владельца видит SSH VM;
- обычный пользователь с sudo и входом по SSH-ключу.

Это исходная конфигурация, а не гарантия времени/памяти для любого полного перебора. При недостатке ресурсов увеличьте RAM/CPU; приложение не заменяет точный анализ выборкой. Не публикуйте VM в интернете на этом этапе.

Установите Docker Engine и Compose plugin из [официального apt-репозитория Docker](https://docs.docker.com/engine/install/ubuntu/). На чистой Ubuntu:

```bash
sudo apt update
sudo apt install -y ca-certificates curl
sudo install -m 0755 -d /etc/apt/keyrings
sudo curl -fsSL https://download.docker.com/linux/ubuntu/gpg -o /etc/apt/keyrings/docker.asc
sudo chmod a+r /etc/apt/keyrings/docker.asc
echo "deb [arch=$(dpkg --print-architecture) signed-by=/etc/apt/keyrings/docker.asc] https://download.docker.com/linux/ubuntu $(. /etc/os-release && echo "$VERSION_CODENAME") stable" | sudo tee /etc/apt/sources.list.d/docker.list > /dev/null
sudo apt update
sudo apt install -y docker-ce docker-ce-cli containerd.io docker-buildx-plugin docker-compose-plugin
sudo systemctl enable --now docker
sudo docker compose version
```

Нужен Compose plugin с поддержкой `up --wait` и `--wait-timeout`. Команды управления ниже запускаются через sudo; добавление пользователя в docker-группу не требуется. Поставки приложения не обновляют Docker и ОС автоматически.

## 2. Собрать релиз

Сборка выполняется на отдельной Linux-машине с Docker, в WSL2 с Docker или на временной VM сборки. На Windows можно использовать Git Bash с доступной командой Docker. На рабочей VM исходники и npm не нужны.

Из корня проекта после проверок:

```bash
npm test
npm run check
bash deploy/vm/build-release.sh v0.1.0 .analysis/releases/v0.1.0
```

Каталог релиза содержит `image.tar`, Compose, `image.env`, управляющий скрипт, smoke-проверку и `SHA256SUMS`. Номер версии должен быть новым; выходной каталог не перезаписывается. Архив образа может занимать сотни мегабайт. Сборка скачивает базовый образ и npm-зависимости, но не отправляет игровые журналы. Разрешительный `.dockerignore` исключает пользовательские файлы, `.git`, `.env`, `.analysis`, тестовые журналы и соседние проекты из контекста.

Базовый образ закреплён на линии Node.js 22 Debian bookworm slim; новая сборка может получить обновления этой линии. Уже выпущенный релиз неизменен благодаря сохранённому архиву и контрольным суммам. Для полного воспроизведения базового окружения в будущем можно закрепить digest базового образа отдельным обслуживанием.

## 3. Передать и установить

На компьютере, видящем VM (замените `user` и `VM_IP`):

```bash
scp -r .analysis/releases/v0.1.0 user@VM_IP:~/domino-release-v0.1.0
ssh user@VM_IP
```

На VM:

```bash
cd ~/domino-release-v0.1.0
sha256sum -c SHA256SUMS
sudo DOMINO_DEPLOY_DIR=/srv/domino bash ./dominoctl.sh install "$PWD"
sudo DOMINO_DEPLOY_DIR=/srv/domino bash ./dominoctl.sh status
sudo DOMINO_DEPLOY_DIR=/srv/domino bash ./dominoctl.sh verify
```

Контрольные суммы проверяйте до исполнения скрипта. Они обнаруживают повреждение, но не подтверждают личность поставщика: используйте собранный вами релиз и доверенный SSH-доступ. Скрипт также проверяет целостность перед загрузкой образа.

`verify` проверяет страницу, скрипты, API, отказ чужим Host/Origin и импорт встроенной учебной партии. Пользовательские файлы не используются и внешних запросов в этой проверке нет. Проверка добавит учебную партию в SQLite. Она не запускает длительный перебор всех раундов.

На VM не нужен внешний registry и не скачиваются образы при установке готового релиза: используется `docker load`, затем Compose с `--pull never`. Docker Hub и npm нужны машине сборки.

## 4. Открыть сайт через SSH

На компьютере владельца, в отдельном терминале:

```bash
ssh -N -o ExitOnForwardFailure=yes -L 127.0.0.1:3210:127.0.0.1:3210 user@VM_IP
```

Откройте [http://127.0.0.1:3210](http://127.0.0.1:3210). Туннель держите открытым. Порт 3210 компьютера должен быть свободен: остановите прежний локальный `npm start`, если он занимает этот порт. Для текущей проверки Host/Origin сохраняйте локальный порт **3210**.

Docker публикует сервис только на `127.0.0.1` VM; прямой переход на `http://VM_IP:3210` не предусмотрен. Внутри контейнера Node слушает `0.0.0.0`, но проверки Host/Origin не отключены. Для будущего публичного доступа потребуются отдельное изменение сетевого контракта, HTTPS и авторизация; не меняйте просто привязку порта на все интерфейсы.

## 5. Обновить и откатить

Соберите следующий номер версии и передайте каталог по SCP. Завершите важный текущий расчёт перед обновлением: перезапуск прервёт незавершённый расчёт, готовые данные останутся в SQLite.

На VM:

```bash
cd ~/domino-release-v0.2.0
sha256sum -c SHA256SUMS
sudo DOMINO_DEPLOY_DIR=/srv/domino bash ./dominoctl.sh update "$PWD"
sudo DOMINO_DEPLOY_DIR=/srv/domino bash ./dominoctl.sh verify
```

Одна команда `update` проверяет релиз, загружает готовый образ, проверяет Compose, копирует каталог примеров в backups и запускает новый контейнер с ожиданием здоровья до 90 секунд. Если образ повреждён/не загрузился, текущий контейнер не заменяется. Если новый запуск не здоров, команда пытается вернуть прежнюю версию и отдельно сообщает об успешности отката; код команды остаётся ненулевым. Healthcheck не продолжает незавершённую рекурсию старого процесса; такой раунд запускается повторно.

Проверка здоровья означает работоспособность HTTP API, но не доказывает отсутствие всех ошибок нового релиза. После автоматического healthcheck используйте `verify` и проверьте нужный сценарий в интерфейсе. Версия с другим содержимым не может занять прежний номер. Образы предыдущих версий не удаляются автоматически, поэтому следите за диском.

Ручной возврат к предыдущей установленной версии:

```bash
sudo DOMINO_DEPLOY_DIR=/srv/domino bash ./dominoctl.sh rollback
```

При успешном откате прежняя текущая версия становится previous, поэтому повторный rollback переключает их обратно. Управляющий скрипт можно запускать из сохранённого каталога релиза; заменять его в системных каталогах не требуется.

## 6. Данные и обслуживание

Структура на VM:

```text
/srv/domino/
  current                 # номер текущего здорового релиза
  previous                # номер предыдущего релиза
  releases/<version>/     # образ и файлы релиза
  data/                   # постоянные domino.sqlite и examples/
  backups/                # копии examples перед заменой контейнера
```

По умолчанию список готовых локальных журналов пуст; учебная партия встроена в приложение. При необходимости **скопируйте**, а не перемещайте, нужные JSON в `data/examples`; процесс внутри образа имеет UID/GID 1000 и должен иметь право чтения. Папка соседнего проекта автоматически не подключается. Перезапуск контейнера не нужен для обновления списка примеров.

Просмотр состояния, последних сообщений и остановка:

```bash
sudo DOMINO_DEPLOY_DIR=/srv/domino bash ./dominoctl.sh status
sudo DOMINO_DEPLOY_DIR=/srv/domino bash ./dominoctl.sh logs
sudo DOMINO_DEPLOY_DIR=/srv/domino bash ./dominoctl.sh stop
```

При намеренной остановке последующий запуск без смены версии:

```bash
sudo DOMINO_DEPLOY_DIR=/srv/domino bash ./dominoctl.sh update ~/domino-release-v0.2.0
```

Автозапуск после перезагрузки обеспечивают Docker systemd service и `restart: unless-stopped`; намеренно остановленный контейнер сам не запускается. Скрипты не удаляют тома, данные, образы или старые релизы. Прежний скрипт копирует только examples; SQLite отдельно сохраняйте через src/backup.js с выгрузкой копии на компьютер. Копии на том же диске не защищают от потери VM: сохраняйте оригинальные JSON и при необходимости копию examples на компьютере владельца.

## Проверено в среде разработки

Проверены настройка bind, сохранение отказов Host/Origin и сценарии управления релизами с подменой Docker: установка, повреждение файла, ошибка загрузки, занятая блокировка, неуспешный healthcheck, возврат к прежней версии, успешное обновление и ручной откат. Диагностический smoke-скрипт также успешно выполнен против отдельно запущенного Node-сервера.

31 октября 2026 года дополнительно проверены настоящая сборка образа linux/amd64 и запуск Compose в Docker Desktop: контейнер healthy, интерфейс доступен с Windows по loopback, smoke-проверка внутри контейнера прошла. Эти результаты не заменяют проверку установки Docker и управления релизами на отдельной Ubuntu VM; такой стенд пока не разворачивался.

## Несколько доверенных клиентов

Каждый клиент открывает собственный SSH-туннель на localhost:3210 по инструкции выше. Расчёты идут в его браузере; отмена одного клиента не затрагивает другие. Библиотека общая, без учётных записей и приватных пространств. Чтобы использовать другой локальный порт, добавьте точный Host в DOMINO_ALLOWED_HOSTS frontend и точный Origin в DOMINO_ALLOWED_ORIGINS backend; wildcard не используется. При npm start DOMINO_ALLOWED_HOSTS передаётся серверу интерфейса. Игровые данные передаются только выбранному серверу.

[Новая роль серверов, API v1, playedAt и замена БД](../../docs/client-computation.md). Старая схема БД при открытии заменяется новой пустой без переноса записей. Перезапуски актуальной схемы сохраняют новые данные; откат прежним релизом требует отдельную БД его схемы.
