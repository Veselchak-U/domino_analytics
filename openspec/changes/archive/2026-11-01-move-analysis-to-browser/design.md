## Context

Мотивация — [proposal.md](proposal.md). Сейчас src/server.js импортирует parseGame, gameSummary и lessonCatalog, владеет единственным worker_threads и SQLite. src/worker.js повторно разбирает журнал и запускает анализ раунда, ветки или упражнения. public/app.js опрашивает серверные jobs и последовательно заказывает раунды. src/input.js зависит от файловой системы, AJV и node:util; игровые модули и solver преимущественно чистые ESM. Ограниченный кеш solver уже сохраняет точность при вытеснении.

Действующие контракты запрещают frontend полный перебор и требуют серверное воспроизведение. Их меняют дельты этого change; основные спецификации до реализации не переписываются. Правила игры, W/N и все существующие сценарии отображения сохраняются.

Прочитан каталог [внешних источников](../../../../docs/domino-analysis-sources.md): смена места вычислений не заимствует minimax, выборку скрытых рук или эвристические оценки. Числа существующих тестов и текущий solver служат регрессионным эталоном переноса, а не внешняя модель домино.

## Goals / Non-Goals

**Goals:**

- Каждый браузер независимо валидирует журнал и считает полное дерево; сервер расходует ресурсы только на ограниченную обработку запросов и SQLite.
- Готовый результат доступен другим доверенным клиентам без повторного расчёта, серверная перезагрузка не останавливает уже начатый локальный анализ.
- Одни игровые правила и формулы для браузера и локального CLI, без Node-зависимостей в браузерном графе импортов.
- Ограниченные память кеша, размеры запросов и число одновременных записей; никаких серверных деревьев, прогресса или глобальной вычислительной очереди.

**Non-Goals:**

- GPU/WebGPU, WASM, распараллеливание одного дерева, распределённые задачи, передача живого кеша и возобновление дерева после закрытия вкладки.
- Публичная регистрация, учётные записи, изоляция библиотек пользователей, рейтинги доверия, серверное доказательство правильности анализа.
- Автоматическая синхронизация между вкладками, постоянный офлайн-режим и гарантированная сохранность неопубликованного результата при закрытии страницы.

## Decisions

### 1. Граница компонентов и владельцы

| Компонент | Владеет состоянием | Чтение / запись | Вычисления и ограничения |
|---|---|---|---|
| Главный поток браузера | Выбор игры/шага, очередь раундов, локальные задания, готовые неопубликованные результаты | REST v1, сообщения worker | Рендеринг, агрегаты, управление; не выполняет solver |
| Модульный Web Worker вкладки | Восстановленная партия, активный запуск, кеш поддеревьев | Получает исходный текст/идентификатор упражнения, отдаёт прогресс/результат | Полная валидация, правила, solver, факты, ветки, учебные проверки; один активный запуск на вкладку |
| Сервер интерфейса | Конфигурация подключения | Раздаёт разрешённые файлы, проксирует API | Не читает SQLite, не запускает solver |
| Backend | Соединение SQLite, короткая очередь записи | Исходные журналы, карточки, готовые результаты | Структурная проверка, хеши, атомарные записи; без игрового ядра и worker |
| SQLite | Общая библиотека и результаты по версиям | Только backend; backup отдельным штатным инструментом | Уникальные ключи, WAL и транзакции |
| Локальный CLI | Собственный запуск и кеш | Локальные файлы, stdout | То же чистое ядро; никогда не используется HTTP-сервером |

Web Worker выбран вместо основного потока ради отзывчивости и возможности жёсткой отмены синхронного рекурсивного обхода. Первый перенос сохраняет один вычислитель на вкладку; глобального ограничения на всех клиентов нет. Дублирующий расчёт двух клиентов допускается: серверные аренды и распределение заданий усложнили бы лёгкий сервис.

### 2. Переносимое ядро и ресурсы браузера

Вынести правила, solver, факты, анализ истории/веток и определения уроков в browser-safe ESM под shared/; текущие src-модули CLI могут стать тонкими адаптерами. Строгий JSON-парсер отделить от Node I/O. JSON Schema поставлять браузеру как заранее сгенерированный валидатор без eval, с проверкой соответствия исходной схеме при разработке. Это сохраняет интерфейс без сборки при запуске и CSP без unsafe-eval. Node-адаптер читает файл; браузерный worker получает текст и использует тот же контракт, без отдельной версии игровых правил.

Frontend раздаёт явный список browser-safe модулей, worker и учебные определения; произвольный доступ к src/, node_modules/, БД или файловой системе запрещён. CSP разрешает worker-src 'self'. Контрактные схемы не содержат игровых данных. Учебный каталог и определения поставляются со статикой и имеют digest набора данных; сервер не строит их через игровое ядро.

Сохранить двухпоколенный кеш и BigInt; значение по умолчанию 250 000 записей, допустимая локальная настройка 2–2 000 000. Это лимит записей, не гарантия объёма heap. Кеш принадлежит одному запуску с одним контекстом начислений, повторный анализ префиксов использует его; новый запуск начинает пустым. Вытеснение вызывает только повторный точный расчёт. При нехватке памяти/сбое worker запуск завершается ошибкой, разрешены повтор с меньшим кешем и просмотр уже готовых раундов; приближённого результата нет.

Для сообщений использовать structured clone и сериализуемый DTO существующего результата: счётчики в десятичных строках, прогресс — ограниченный объект, без передачи Map кеша. BigInt используется внутри вычислителя и точных сравнений. Идентификатор запуска и поколение выбора партии сопровождают каждое сообщение: поздние ответы старого запуска игнорируются.

### 3. GPU не является прозрачной заменой solver

Базовый движок работает на CPU в Web Worker, без требования navigator.gpu. Текущий обход, Map и JavaScript BigInt нельзя непосредственно исполнить как WGSL-шейдер. В [спецификации WGSL](https://www.w3.org/TR/WGSL/) описаны конкретные числовые типы без JavaScript BigInt; поэтому точный GPU-вариант потребует отдельного представления больших чисел и алгоритма работы с нерегулярным деревом. Это вывод для нашего алгоритма, а не заявление, что точный GPU-перебор невозможен.

В этом change отсутствие GPU даёт те же точные результаты. Архитектура отделяет вызов вычислителя от UI и хранения, чтобы последующий GPU-движок мог сохранять тот же DTO. Его будущая приёмка потребует совпадения всех точных счётчиков, дедупликации, кратности, исходов и отмены с CPU-эталоном; ускорение измеряется отдельно. Наличие GPU само по себе не обещает ускорения.

### 4. API v1 и идентичность результатов

Переработать существующую первую версию API на месте: основной префикс /api/v1 сохраняется, /api остаётся его алиасом с теми же ответами и ошибками. Версия HTTP API остаётся 1; envelope результата и версии правил/движка/метрик/схемы payload учитываются независимо. Новый envelope имеет formatVersion=1. Версии математического контракта учитываются независимо от версии HTTP API; старые записи БД по указанию пользователя не переносятся. API v1 больше не имеет вычислительных заданий. Сохранение номера API не означает совместимость со старым UI: контракт меняется вместе с релизом клиента и сервера.

Источник входного контракта — [domino_spec](../../../../docs/game-spec-source.md), проверенная ревизия 0ea1fffe3262107562029cb401b9a39f354f62f4. Локальная схема синхронизирована с playedAt; standalone-валидатор реально проверяет format:date-time. Позиция playedAt первым ключом — соглашение записи, не условие приёма. Само поле обязательно, отсутствующая дата не подменяется временем импорта.

Идентичность партии: `{playedAt: normalizedInstant, players: sortedNames}`. Время нормализуется в UTC с сохранением всей дробной точности без округления до миллисекунд; равные моменты с разными смещениями и незначащими нулями имеют одинаковое представление. Имена берутся из teams[].players[].name, сравниваются точно с учётом регистра и пробелов, без trim/смены регистра; четыре различных имени сортируются единым порядком Unicode code points, без локализованной сортировки. Порядок объектов teams/players, места, названия команд, имя файла и дата импорта не входят в идентичность. Некорректные имена/повторы отклоняются как минимальная проверка ключа. gameId — SHA-256 канонического объекта этой идентичности, а не хеш исходного текста.

Для защиты сохранённых расчётов отдельно хранится digest содержимого журнала. Он вычисляется по разобранному JSON с нормализованным playedAt, рекурсивно упорядоченными ключами объектов, teams по техническому id, players по seat и отсортированными камнями внутри каждой начальной руки. Порядок раундов и ходов сохраняется. Эта нормализация учитывает соглашения источника о незначимости порядка teams, players и камней раздачи; она не переписывает исходный текст в БД. Разные отступы, порядок ключей и равное время в другом часовом поясе не создают конфликт. Любое отличие остальных значений, включая места/команды, правила, ходы и итоги при той же идентичности, даёт 409 GAME_SOURCE_CONFLICT: не создавать вторую партию, не заменять первый исходник и не прикреплять результат к другому содержимому. Новый контент не объявляется проанализированным по прежнему кешу. Эквивалентный повтор возвращает первый исходный текст/метаданные и использует прежние результаты. Хеш сырых байтов можно хранить для проверки сохранности, но он не определяет идентичность партии.

| Операция | Контракт |
|---|---|
| GET /api/v1/health | Доступность БД, версия API и поддерживаемая версия результата |
| GET /api/v1/games?limit=…&cursor=… | Стабильные страницы карточек; готовность только по сохранённым совместимым раундам |
| POST /api/v1/import | {text,name}; 201 для новой партии, 200 при эквивалентном повторе идентичности playedAt + игроки; 409 GAME_SOURCE_CONFLICT при другом содержимом той же партии |
| GET /api/v1/games/:id | Карточка; summary — проекция полей исходного JSON, без воспроизведения и отметки игровой проверки сервером |
| GET /api/v1/games/:id/source | Точный исходный текст, 404 для неизвестной партии |
| GET /api/v1/games/:id/analyses?limit=…&cursor=… | Постраничный manifest готовых совместимых раундов: номер, key, версия и hash, без payload; клиент читает нужные envelope через results |
| GET /api/v1/results/:key | Готовый envelope или 404; несовместимые результаты не выдаются как актуальные |
| PUT /api/v1/results/:key | Структурно проверенный завершённый envelope; 201 при первой записи, 200 при эквивалентном повторе, 409 при другом содержимом того же ключа |
| GET /api/v1/examples и GET /api/v1/examples/:id/source | Список и чтение разрешённого локального примера или встроенного demo; чтение не импортирует игру и не анализирует её |

Envelope: formatVersion=1, descriptor, result, payloadHash, provenance. Descriptor содержит version={rules,engine,metrics,schema} и kind:

- round: gameId, round;
- branch: gameId, round, position, упорядоченные moves, example (null/win/loss/draw);
- lesson: lessonId, lessonDataHash, mirror.

Ключ — SHA-256 канонического descriptor. Канонизация: UTF-8 JSON без пробелов, ключи объектов рекурсивно лексикографически упорядочены, порядок массивов сохранён; отсутствующие обязательные поля не заменяются неявными defaults. Все числа descriptor — безопасные целые, необязательные значения нормализуются клиентом до явных null/false/[] по схеме. Один общий модуль канонизации применяется клиентом и сервером.

payloadHash считается так же по result без корневого stats: runtime-статистика (время, число cache hits и оценка памяти) может различаться между устройствами, но не делает математический результат другим. Все прочие поля включаются в hash. Provenance, назначаемый сервером, содержит producer=browser и verification=structural-only. Эти поля не являются сертификатом правильности. При эквивалентном повторе сохраняются первый result/stats и provenance; ответ явно возвращает существующий envelope.

Ошибки: 400 — JSON/схема/хеш/ключ/связь с источником, 404 — неизвестная игра/результат/пример, 409 — конфликт результата или содержания партии, 413 — превышение размера, 415 — неподдержанный Content-Type, 422 — неподдерживаемая версия, 429 — временно заняты оба слота загрузки, 503 — хранилище недоступно. Тело ошибки содержит стабильный code и русский error, без внутреннего SQL. Для 429/503 клиент сохраняет локальный результат и предлагает повтор публикации; конфликты не перезаписываются автоматически.

Каталог и manifest анализа имеют limit по умолчанию 20 и максимум 100, стабильную курсорную сортировку, не включают payload результатов. Один GET results читает не более одного envelope. Клиент последовательно подгружает готовые раунды для сводки партии и не требует от backend сформировать одним ответом все анализы. Это ограничивает пиковую память чтения размером одного результата и страницы метаданных.

### 5. Минимальная серверная проверка и предел доверия

Сервер проверяет транспорт, строгий JSON без повторных ключей, разрешённые поля, типы, размеры, поддержанные версии, формат decimal-строк и SHA-256, существование игры, номер раунда и индекс в границах исходного массива, структуру пути/урока. Для исходного журнала применяет контрактную JSON Schema, но не проверяет очередь, все 28 камней, законность пасов, начисления или итог игровым воспроизведением. Карточка не выдаёт присланный summary за вычисленный: берёт названия и заявленные итоги из исходного JSON, validation=structural-only. Метаданные, нужные для подробного отображения (например, analyticsWinner), восстанавливает клиент.

Для result схема ограничивает массивы и вложенность, шаги/альтернативы и обязательные поля. Сервер линейно сверяет дешёвые инварианты каждого распределения: положительное leaves; неотрицательные wins/outcomes; суммы исходов равны leaves и wins, fish/eggs согласованы; minDepth <= depth, терминальные длины 0. Принимаемые decimal-строки имеют не более 1024 цифр; числовые показатели конечны. Проценты для отображения клиент выводит из точных счётчиков. Сервер не применяет игровые ходы и не проверяет полноту дерева. Клиентский флаг «проверено» не изменяет provenance.

Лимиты: исходный текст <=5 МиБ UTF-8, тело импорта <=11 МиБ, результат/envelope <=16 МиБ; глубина JSON <=64, не более 1024 раундов и 128 действий на раунд/ветку, не более 129 шагов и 56 альтернатив на шаг. Эти ограничения фиксируются в контрактах API v1 и проверяются до дорогих операций; большее значение даёт явную ошибку, без усечения результата. Сначала потоковый лимит байтов, затем ограниченная проверка глубины/повторных ключей, затем разбор/схема/инварианты. Сжатые тела не принимаются. Два одновременных изменяющих запроса на процесс, превышение — 429 до чтения тела; чтения не занимают эти слоты. Настройка сервера не уменьшает лимиты молча: несовместимый размер возвращает ошибку и оставляет локальный результат.

Структурно согласованный поддельный результат может пройти эту границу: хеш подтверждает идентичность байтов, а не правильность анализа. Принята общая библиотека доверенных клиентов, как продолжение текущего приложения одного владельца. Первый корректный по структуре результат по ключу не перезаписывается; 409 показывает проблему для ручного разбора. Авторитетная серверная перепроверка потребовала бы отдельного вычислительного сервиса и противоречила бы выбранной роли backend.

### 6. Последовательность работы браузера

1. Загрузка файла, источника из библиотеки или примера; полная валидация в worker до расчёта и обычной публикации нового журнала. Некорректный журнал показывает прежние контекстные ошибки и не меняет текущую открытую игру. Прямой сторонний API-клиент может сохранить структурно корректный, но игровой неверный журнал; при открытии браузер его отклоняет.
2. После проверки нового источника — POST import; при недоступном сервере анализ всё равно возможен локально, исходный текст удерживается до публикации. По умолчанию загрузка файла означает сохранение в выбранной библиотеке, как сейчас; дополнительных подтверждений на каждую запись нет.
3. Для каждого раунда/ветки/урока сначала локальная память, затем GET result; найденный envelope проверяется по структуре, digest и совместимости. Для раунда/ветки исходный журнал всё равно должен пройти полное клиентское воспроизведение. Полного повторного перебора скачанного результата нет: это разделяемый клиентский кеш с указанной границей доверия.
4. При отсутствии кеша локальный worker выполняет расчёт. Прогресс и отмена не используют REST. Первый раунд автоматически, оставшиеся — последовательной очередью вкладки, как в текущем UI.
5. Готовый анализ отображается сразу. Состояния разделены: «рассчитано локально», «сохраняется», «сохранено на сервере», «не сохранено», «конфликт». Готовность в серверном каталоге меняется только после подтверждения записи. При потере ответа PUT проверка GET/повтор PUT безопасны.
6. Если исходник ещё не сохранён, сначала повторяется POST import, затем PUT result. Пользователь может повторить публикацию без solver. Разрыв сети не отменяет CPU-расчёт; сохранение не блокирует навигацию.

Локальные состояния запуска: idle → validating → checking-cache → running → computed; из running возможны cancelled/error. Сохранение — отдельный автомат pending → uploading → saved/unsaved/conflict. Отмена вычисления завершает worker и инвалидирует runId; новый worker позволяет повтор. Закрытие вкладки теряет активное дерево и неопубликованные данные; сервер не сохраняет фиктивный running job и не обещает продолжения с чекпойнта. Готовые серверные раунды переживают закрытие вкладки.

### 7. Несколько клиентов, запись и сеть

Нет active на сервере и нет блокировки ключа на время клиентского анализа. Идентичность партии имеет уникальное ограничение БД; при импорте эквивалентность или конфликт проверяются атомарно. Короткая транзакция проверяет существующий ключ и вставляет готовый результат с уникальным ограничением; первая фиксация побеждает, эквивалентный повтор идемпотентен, различие даёт 409. INSERT OR REPLACE для общего результата запрещён. Тело не разбирается под транзакцией. SQLite busy_timeout ограничен; при неуспехе — повторяемая ошибка хранения. В память backend не загружается вся библиотека; чтения страниц и готовых результатов ограничены запросом.

Локальная и VM-поставка сохраняет два сервиса, постоянный том и закрытый доступ. Несколько клиентов подключаются собственными SSH-туннелями; статические ресурсы и API доступны под одним origin каждого туннеля, допустимые Host/Origin настраиваются явным списком, wildcard не добавляется. По умолчанию сохраняется localhost/loopback. Удалённая передача игровых данных разрешена только выбранному владельцем серверу библиотеки; внешние сервисы и телеметрия не используются. Публикация в открытый интернет и внешний HTTPS ingress требуют отдельной модели доступа.

### 8. Матрица режимов и приёмка

| Условие | Наблюдаемое поведение | Покрытие |
|---|---|---|
| Совместимый серверный кеш | Проверить журнал и envelope, показать готовый результат без solver | API + браузер |
| Кеша нет, сервер доступен | Локальный точный расчёт, прогресс, затем публикация | worker + сквозной |
| Сервер пропал после загрузки страницы и исходника | Расчёт продолжается, результат доступен, публикация повторяется | браузер с отключением API |
| Два клиента считают разные ключи | Оба локальных запуска идут; каталог и чтения отвечают без вычислительного 409 | два browser context + API |
| Два клиента публикуют один ключ | 201/200 при равном hash, 201/409 при различном; одна запись | конкурентный API |
| Нет GPU | Полный CPU-расчёт с теми же точными счётчиками | browser CPU-only |
| Нет Worker/BigInt или worker не загрузился | Явная ошибка вычислителя, просмотр готовых данных где поддержан; никакого серверного fallback | браузер с отказом worker |
| Отмена/ошибка worker | Нет публикации частичного результата; готовые данные сохранены, повтор доступен | worker + браузер |
| Вкладка закрыта | Активный расчёт утрачен; сохранённые в актуальной схеме результаты доступны при новом открытии | браузер |
| Старый UI вызывает удалённый вычислительный маршрут | 410 CLIENT_COMPUTATION_REQUIRED с требованием обновить страницу; актуальные маршруты API v1 продолжают работать | API совместимости |
| Запрос через алиас /api | Тот же контракт, что через /api/v1; библиотека, health и результаты доступны | API алиаса |

N/A: восстановление активного дерева после перезапуска и вычисления на сервере — отсутствуют по контракту. GPU-ускоренный режим отсутствует в этом change; CPU-only является полноценным режимом.

Регрессионный эталон test/fixtures/real-game.json: 7 328 406 листьев, wins [4 255 456, 3 072 949, 1], depth=40, 16 шагов. Дополнительно — существующие независимые проверки рыбы, яиц, ничьей партии, ориентации, дедупликации, кратности, исходов, BigInt, ветвей и уроков. Время/узлы/попадания кеша между устройствами сравнивать как статистику, не как обязательное математическое равенство.

Профиль нагрузки: два независимых клиента считают полный реальный раунд, параллельно третий читает health/каталог/готовый результат; затем две одновременные публикации. Зафиксировать CPU/RSS backend, размер БД и задержки относительно простоя на указанном оборудовании; серверная CPU-нагрузка не должна зависеть от числа узлов клиентского дерева, и в серверном процессе нет вычислительных потоков. Измерения не дают универсальной гарантии задержки на любом сервере; лимиты запросов обеспечивают ограниченную работу на одну операцию.

## Risks / Trade-offs

- [Общий кеш доверяет клиенту] → явно отделять structural-only от математической проверки; сохранять digest/provenance и обнаруживать конфликт без перезаписи.
- [Большой раунд может исчерпать память браузера] → ограниченный кеш, жёсткая отмена и повтор с меньшим лимитом; точность не снижается.
- [Закрытие вкладки теряет неопубликованное] → явный статус сохранения и предупреждение при уходе с активной/несохранённой работой в пределах возможностей браузера; постоянный локальный outbox вне объёма.
- [Два клиента дублируют работу] → разрешённая плата за отсутствие координатора; проверка готового кеша перед запуском и идемпотентная запись.
- [Крупные JSON и синхронная SQLite создают короткую нагрузку] → байтовые/структурные лимиты, два слота загрузки, короткие транзакции и измерение профиля. Не утверждать, что сервер вообще не расходует CPU.
- [Старый кеш браузера смешивает версии модулей] → версия URL статических модулей/worker, загрузка единого релиза и 410 только для удалённых серверных вычислений, без service worker со старым вычислителем. Каталог, импорт и чтение результатов продолжают работать в переработанном API v1.

## Database Replacement and Deployment

По указанию пользователя миграция и legacy-хранилище исключены. При открытии схемы старше текущей поддерживаемой версии приложение отказывает; при версии ниже 3 транзакционно удаляет прежние таблицы и создаёт только games/results по новой схеме, затем освобождает старые страницы БД. Старые журналы, результаты и jobs не переносятся и не сохраняются в legacy. При версии 3 повторное открытие сохраняет актуальные данные.

Frontend и backend поставляются совместно с переработанным API v1 и алиасом /api. Удалённые вычислительные маршруты и POST /example возвращают 410 CLIENT_COMPUTATION_REQUIRED. Demo читается через GET examples/demo/source, локально проверяется и публикуется через POST import. URL health сохраняется. Возврата к worker_threads в HTTP-процессе нет.

Обновить контейнеры и команды управления, проверить новую пустую библиотеку после замены старой схемы, повторное открытие актуальной БД без потери новых записей, backup и независимых клиентов. Автоматический перенос данных при откате не предусмотрен: прежний релиз требует отдельную БД своей схемы. Рабочие пользовательские JSON на диске не изменяются.

После успешного запроса worker остаётся загруженным и используется повторно; новый solver получает пустой кеш и новый контекст на каждый запуск. Это сохраняет возможность вычисления уже загруженным модулем при отказе API. Отмена/ошибка завершает worker, следующий запуск создаёт новый.
