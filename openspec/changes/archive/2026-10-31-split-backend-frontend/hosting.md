## Зафиксированный формат

- Виртуальная машина с полноценным Linux и root/SSH; предпочтительно KVM или эквивалентная VM с поддержкой Docker. Общий PHP-хостинг не подходит.
- Ubuntu Server 24.04 LTS, x86-64; Docker Engine из официального apt-репозитория и Compose plugin. Docker Desktop на сервере не нужен. [Поддержка ОС и архитектур](https://docs.docker.com/engine/install/ubuntu/).
- Начальная целевая конфигурация: 2 vCPU, 4 ГБ RAM, SSD от 30 ГБ. Это инженерная отправная точка, не доказанная достаточность для всех раундов. Нужны измерения полного перебора. Для вычислителя предпочтительна гарантированная доля CPU 100%; малая доля увеличит длительность без изменения точности.
- Основной формат образов `linux/amd64`, соответствующий целевому российскому VPS. `linux/arm64` — дополнительный вариант сборки при фактической потребности, не обязательная зависимость от Oracle. [Многоплатформенные образы](https://docs.docker.com/build/building/multi-platform/).
- Два приложения: `frontend` (статические файлы и Caddy) и `backend` (Node.js, worker_threads, SQLite). БД — файл на диске бэкенда, отдельный контейнер БД не требуется. Kubernetes и специальный образ всей VM для первого размещения не нужны.
- Поставка: `compose.yaml`, конфигурационные шаблоны, описание релиза с digest образов, утилита управления. Секреты и данные хранятся отдельно от релиза.

## Размещение и доступ

Первый запуск без покупки домена: контейнер фронтенда опубликован только на `127.0.0.1:8080` VM; доступ через SSH-туннель. Caddy направляет `/api/v1/*` во внутренний `backend:3210`, остальные запросы обслуживает статикой. Порт бэкенда на хосте не публикуется. Владелец открывает `http://127.0.0.1:8080` на своём компьютере; пароль и журнал проходят внутри шифрованного SSH-соединения. Вход приложения также обязателен.

Публичный режим: свой домен, HTTPS и вход владельца. Фронтенд и API могут иметь разные имена и находиться у разных российских провайдеров. Отдельно размещённый API получает собственный TLS ingress; фронтенд меняет runtime `apiBaseUrl`, API — список разрешённых origins. В штатном режиме публикуются только 80/443, SSH ограничивается административным доступом. Docker-порты не следует защищать только правилами UFW: [документация Docker описывает обход этих правил опубликованными портами](https://docs.docker.com/engine/install/ubuntu/).

## Обновления

В реализации появится команда `dominoctl update <релиз>`. Сейчас её ещё нет. Обычный цикл:

1. На машине сборки или в CI выполнить проверки и собрать образы; выпустить неизменяемый релиз с версиями, digest, диапазоном схемы БД и API. Из образов исключить журналы, соседние каталоги, `.env`, резервные копии и инструменты разработки.
2. Доставить релиз в российский OCI registry по выбору владельца. Базовый вариант без обязательного registry: архив образов через `docker save`, переданный по SCP на VM; загрузка через `docker load`. Обновление не зависит от доступности GitHub/Docker Hub непосредственно на рабочем сервере. Базовые образы нужны на стадии сборки.
3. Утилита проверяет checksum/digest, свободное место, совместимость и блокировку другого обновления. До остановки скачать/загрузить все целевые образы. При ошибке текущая версия продолжает работать.
4. Перевести API в обслуживание: запретить новые записи/задания и остановить диспетчер. Активный раунд по умолчанию дождаться; по тайм-ауту отменить обновление и вернуть рабочий режим. Явный параметр владельца позволяет прервать раунд с последующим точным пересчётом. Для этой стадии нужен наблюдаемый статус, а не бесконечное молчаливое ожидание.
5. Создать согласованный backup SQLite, проверить целостность. Остановить старый API, выполнить миграции одноразовой командой из нового backend-образа, запустить нужные сервисы через Compose и дождаться healthchecks. Compose поддерживает [обновление контейнеров с сохранением смонтированных томов](https://docs.docker.com/reference/cli/docker/compose/up/); [pull](https://docs.docker.com/reference/cli/docker/compose/pull/) только скачивает образы.
6. Проверить вход, чтение библиотеки и сохранённого анализа, затем разрешить записи и очередь. Записать текущую/предыдущую версии. При неуспехе сохранять режим обслуживания до отката.

Обновлять только фронтенд или только API можно в пределах совместимого `/api/v1`. Первая схема обновления допускает короткий перерыв; бесшовность на одной VM не обещается. Не применять бесконтрольное автообновление образов по `latest`.

Откат: прежние digest и конфигурация; если прежний API совместим с новой БД — вернуть образы. Иначе остановить API и восстановить проверенный backup до миграции, затем старые образы. Автоматический откат допустим только до открытия записей; после открытия нужен выбор владельца, поскольку восстановление старой копии потеряет новые записи. Не удалять тома и не выполнять `docker compose down -v` при обновлении.

## Постоянные данные и перенос

`/srv/domino/data/` — SQLite с WAL, `/srv/domino/backups/` — локальные согласованные копии, `/etc/domino/` — защищённые настройки и секреты, `/opt/domino/releases/` — версии поставки. Права записи на данные имеет backend; frontend их не монтирует. Backup через SQLite Online Backup API, а не копирование одного открытого `.sqlite` без WAL. [Обоснование SQLite](https://sqlite.org/backup.html).

Ежедневная копия, 7 ежедневных и 4 недельных; отдельная копия перед обновлением. Как минимум одну актуальную копию переносить за пределы VM: на компьютер владельца или российское хранилище, выбранное им. Локальная копия не защищает от потери VM. До первого размещения проверить восстановление; ёмкость SSD и резервные копии входят в расчёт стоимости.

Переезд: остановить записи, сделать согласованную копию, перенести её и конфигурацию по SSH, установить Docker на новую VM, загрузить те же образы и запустить Compose. Проверить библиотеку и счётчики, затем переключить DNS/туннель. SQLite подключается только к одному экземпляру API на одном хосте; общий сетевой диск между двумя API не поддерживается. При потребности в нескольких репликах API отдельно мигрировать на PostgreSQL.
