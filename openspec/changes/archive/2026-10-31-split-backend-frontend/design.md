## Context

src/server.js владеет Map игр/задач/результатов и worker, а также раздаёт public. src/analysis.js и lessons.js импортируют чистые функции из public. Браузер последовательно рассчитывает раунды, поддерживает отмену и тренировки. См. proposal.md.

## Goals / Non-Goals

**Goals:** два независимых приложения и образа; неизменные исходники игр; долговечные результаты; восстановление библиотеки; удобное управление в Windows.

**Non-Goals:** облака, публичная авторизация, FIFO-очередь, автоматическое продолжение незавершённой рекурсии, межпартийная статистика, изменение критериев анализа. Точная аналитика остаётся на backend; чистые производные показатели отображения и проверки учебного выбора сохраняют текущие формулы.

## Decisions

### Сервисы и общие функции

Frontend — отдельный Node HTTP-сервер без npm-зависимостей: статика public и shared, runtime-config и прокси /api на заданный backend. Backend — API без раздачи статики. Чистые функции impact/domino/tactics вынесены в shared; public-модули оставляют совместимые re-export для прежних импортов и тестов. Backend-образ не содержит public, frontend не содержит игровых журналов/solver/БД.

Отдельные команды npm run start:backend и start:frontend; npm start запускает оба HTTP-сервера для обычной разработки. Снаружи по-прежнему порт 3210. Разделение каталогов src/public/shared достаточно для независимой упаковки, перенос в apps/* не создаёт дополнительной ответственности.

### Владение состоянием

| Компонент | Владелец | Чтение/запись |
|---|---|---|
| API | HTTP-входы, проверка Host/Origin | Читает/пишет через SQLite repository |
| Backend | Единственный worker, память кеша результатов | Публикует только завершённый результат после commit |
| Worker | Solver и кеш поддеревьев | Не имеет доступа к SQLite |
| SQLite repository | Одно соединение записи, миграция схемы | Игры, задания, версии, результаты |
| Frontend | Выбранная игра, шаг и экран | REST; не читает файл БД |

### SQLite

Используется встроенный node:sqlite (DatabaseSync), без внешнего native-драйвера. Для Node.js 22 эта возможность экспериментальная; совместимая минимальная версия 22.13, локально проверена 22.15.1. PRAGMA WAL, foreign_keys, busy_timeout; schema_migrations управляет первоначальной схемой и отвергает более новую неизвестную версию. База хранится в /data/domino.sqlite в именованном Docker-томе. Несколько реплик backend не поддерживаются.

Таблицы: games(id SHA-256 текста PRIMARY KEY, text, file_name, summary_json, created_at); results(key PRIMARY KEY, game_id nullable, round_number nullable, kind, version, payload_json); jobs(id PRIMARY KEY, key, status, stats_json, error, cached, interrupted). Готовый result и done-job записываются одной транзакцией. На ошибке commit результат не появляется в кеше памяти. Неверный импорт проверяется до INSERT.

Исходный text сохраняется без JSON.parse/stringify на клиенте. Точный повтор байтов имеет тот же id и первое имя файла. Разное форматирование — другая игра. Все вычислительные BigInt уже сериализуются строками текущим summarize; repository сохраняет JSON без преобразования точных строк в Number.

Ключ кеша содержит явную версию правил/движка/метрик/результата, id игры, номер раунда, полный путь ветви и режим либо id/mirror урока. Память bounded, БД долговечна. API каталога считает готовые раунды только текущей версии. Старые результаты не удаляются и не выдаются за актуальные; после изменения версии выполняется новый расчёт.

### Задания и восстановление

Текущие API-статусы running/done/error/cancelled сохраняются. GET задания после перезапуска доступен из БД. Сохраняется последнее периодическое значение progress, финальные переходы пишутся сразу. Оставшиеся running при старте отмечаются error, interrupted:true. При явном повторе создаётся новый worker; завершённые раунды загружаются из БД. Закрытие вкладки не останавливает начатый worker; дальнейшие ещё не заказанные раунды рассчитываются при открытии игры. Новую серверную очередь не добавляем.

Один backend владеет не более одним worker; одинаковый активный запрос возвращает его job, другой — 409, как раньше. Зафиксированная отмена исключает поздний результат. close останавливает worker, отмечает прерывание и закрывает БД. Ошибочные/отменённые результаты не кешируются.

### API и безопасность

Контракт в api.md. /api/v1 — основной префикс; /api остаётся alias. Frontend проксирует только на фиксированный backend URL, сохраняя Origin и передавая ожидаемый Host. Оба сервера проверяют Host/Origin; разрешённые origins backend задаются конфигурацией. По умолчанию backend доступен лишь внутри Docker; frontend — loopback. Прокси не принимает произвольную цель из запроса. CORS для явно разрешённого origin поддерживает прямой доступ в локальном режиме без отключения проверок. Публичный доступ требует будущего изменения безопасности.

Frontend берёт apiBaseUrl из runtime-config; по умолчанию /api/v1. Конфигурация не содержит секретов. CSP разрешает соединение только с self и явно заданным API-origin. Состояние выбранного id можно помнить в localStorage; игровые данные источником истины в браузере не становятся.

### Интерфейс и поставка

Список сохранённых игр с дозагрузкой страниц, имя и число готовых раундов. При открытии сначала загружаются готовые раунды; первый готовый отображается без worker, недостающие рассчитываются по прежней последовательности. Ошибка сети не стирает прошлую открытую игру.

В корне start-docker.cmd, stop-docker.cmd, update-docker.cmd, restart-docker.cmd, status-docker.cmd, logs-docker.cmd, backup-docker.cmd вызывают общий PowerShell-скрипт. Он находит Docker Desktop, проверяет движок и управляет Compose. Stop/update/restart не выполняют down -v. Backup использует VACUUM INTO из отдельного соединения SQLite и экспортирует копию на компьютер. Игровые файлы не включены в контекст сборки.

Прежняя одноконтейнерная VM-поставка поддерживает npm start (два сервера внутри одного legacy-образа); текущая поставка Desktop использует два независимых образа. Дальнейший перенос VM не выполняется.

### Матрица

| Режим | БД | Сеть |
|---|---|---|
| Тест createApp без пути | :memory: | Случайные loopback-порты |
| npm start | .analysis/domino.sqlite | frontend 3210, backend 3211 loopback |
| Docker Desktop | Постоянный том /data | frontend 127.0.0.1:3210, backend только внутренняя сеть |
| Отдельные процессы | Явный DATABASE_PATH | Явные адреса/allowed origins |
| Облака/несколько пользователей | Не реализуется | N/A в этом изменении |

## Risks / Trade-offs

- Полный перебор может быть долгим → текущие progress/отмена, точность не заменяется выборкой.
- Перезапуск обрывает текущий раунд → явная ошибка и повтор; готовые результаты сохранены.
- Старый контейнер держал данные только в памяти → оригинальные файлы нужно повторно импортировать; новая база не объявляется миграцией Map старого процесса.
- Потеря тома → команда резервной копии; обычные команды том не удаляют.
- Экспериментальность node:sqlite в Node 22 → узкая проверенная поверхность SQL и тесты на хосте и в образе.

## Migration Plan

Сначала контрактные падающие тесты, затем repository, API, frontend и Docker. Проверить исходные точные результаты, перезапуск/recreate контейнеров, повтор импорта и кеш. Сменить работающую старую группу domino-local на два сервиса без удаления томов, открыть прежний URL. Архивировать change после проверок. Исследование hosting.md не является инструкцией облачного размещения.
