# game-library Specification

## Purpose
Обеспечить постоянную общую библиотеку исходных журналов и компактных результатов с идентичностью по времени начала партии и составу игроков.

## Requirements

### Requirement: Постоянный проверенный импорт
Бэкенд SHALL принимать исходный kozel-game-v1 до 5 МиБ UTF-8 с телом HTTP до 11 МиБ, проверять строгий JSON без повторных ключей, схему, типы, имя файла и ограниченные размеры массивов, но MUST NOT воспроизводить игровые переходы или проверять начисления игровым ядром. Глубина JSON SHALL быть не более 64, число раундов — 1024, действий в раунде — 128. Исходный текст SHALL сохраняться неизменным; серверная отметка проверки SHALL быть structural-only. Неверный структурный импорт MUST NOT создавать игру. Идентичность партии SHALL определяться нормализованным моментом playedAt и неупорядоченным составом четырёх уникальных имён игроков из teams[].players[].name. Повтор этой идентичности с эквивалентным содержимым SHALL возвращать прежний id, первое имя файла, дату загрузки и исходный текст без дубликата; отличающееся игровое содержание SHALL давать 409 GAME_SOURCE_CONFLICT без перезаписи и без выдачи прежнего анализа за анализ нового содержания. Браузер SHALL выполнять полное воспроизведение до обычной публикации и анализа; структурно принятый через прямой API игровой неверный журнал SHALL отклоняться браузером при открытии. Карточка сервера SHALL содержать только проекцию заявленных полей журнала и готовность сохранённых результатов, без утверждения вычисленного сервером итога.

#### Scenario: Импорт, повтор и перезапуск
- **WHEN** файл импортирован дважды и backend перезапущен с той же БД
- **THEN** каталог содержит одну игру, метаданные и исходный текст совпадают с первым импортом, серверная проверка обозначена как структурная

#### Scenario: Неверный файл и границы
- **WHEN** JSON имеет повторный ключ, нелегальный ход, неверные начисления либо превышает лимит
- **THEN** повторный ключ/лимит отклоняется сервером; нелегальный ход и неверные начисления отклоняются полной проверкой браузера до обычной публикации, каталог при обычном импорте не пополняется

#### Scenario: Прямой API с игровым нарушением
- **WHEN** сторонний клиент сохраняет структурно корректный журнал с неверной очередью, затем пользователь открывает его в браузере
- **THEN** сервер не выполняет игровую проверку, браузер сообщает нарушение и не запускает анализ, исходный текст остаётся неизменным

#### Scenario: Одновременный повтор источника
- **WHEN** два клиента одновременно публикуют одну партию с разным форматированием JSON и разными именами файлов
- **THEN** создаётся одна игра с именем первой зафиксированной записи; оба получают один id

### Requirement: Открытие сохранённых игр
Интерфейс SHALL показывать сохранённые игры с именами и готовностью анализа и позволять открывать их без повторного выбора файла. API SHALL предоставлять стабильные страницы каталога и точный исходный текст; неизвестная игра SHALL возвращать 404.

#### Scenario: Сохранённая игра в интерфейсе
- **WHEN** страница перезагружена и владелец выбирает ранее сохранённую игру
- **THEN** отображаются прежний журнал и доступные результаты, повторная загрузка файла не требуется

#### Scenario: Страницы и неизвестный id
- **WHEN** запрошены страницы фиксированного каталога, неверный курсор либо неизвестная игра
- **THEN** страницы не дублируют записи, неверный курсор даёт 400, неизвестная игра даёт 404

### Requirement: Идентичность по времени начала и игрокам
Импорт SHALL требовать playedAt по актуальному контракту domino_spec: начало партии по RFC 3339 с часовым поясом и включённой проверкой date-time. Отсутствие поля, null, пустая строка, недопустимая дата или отсутствие пояса SHALL давать 400 до сохранения. Позиция поля первым в объекте SHALL не влиять на приём. Идентичность SHALL включать один нормализованный момент начала без потери дробной точности и отсортированные четыре уникальных имени игроков. Порядок команд/игроков, имя файла и оформление JSON SHALL не менять идентичность; регистр и пробелы внутри имён SHALL сохранять значение. Изменение момента или состава игроков SHALL создавать другую идентичность. При эквивалентном повторе SHALL сохраняться первый исходный текст, имя, дата загрузки и совместимый кеш. При различном игровом содержимом той же идентичности SHALL возвращаться 409 GAME_SOURCE_CONFLICT без перезаписи, дубликата и повторного использования прежнего кеша для изменённого журнала. Старые записи БД SHALL не переноситься; импорт исходного файла без playedAt SHALL требовать явной даты без подстановки времени загрузки.

#### Scenario: Равный момент и оформление
- **WHEN** одна партия повторно импортирована с playedAt 2026-09-12T19:30:00+03:00 вместо 2026-09-12T16:30:00Z, другими отступами и порядком ключей/объектов команд и игроков
- **THEN** возвращаются один gameId, первый исходник/метаданные и прежний совместимый анализ без дубликата

#### Scenario: Другая партия и точность времени
- **WHEN** изменено одно имя либо момент начала, включая различие в дробных секундах после миллисекунд
- **THEN** идентичность отличается; дробная точность не теряется при нормализации

#### Scenario: Совпавшая идентичность с другим содержимым
- **WHEN** при том же моменте и тех же игроках изменены ходы, места, правила или результаты
- **THEN** сервер возвращает 409 GAME_SOURCE_CONFLICT, прежние исходник и анализ не меняются, второй журнал не сохраняется как новая партия

#### Scenario: Отсутствующая дата и порядок полей
- **WHEN** playedAt отсутствует, некорректно или не имеет пояса либо корректное playedAt находится не первым ключом
- **THEN** первые случаи отклоняются без значения по умолчанию, последний принимается

#### Scenario: Старая партия без даты
- **WHEN** пользователь повторно импортирует исходный файл без playedAt после замены БД
- **THEN** импорт отклонён без подстановки createdAt/mtime, пользовательский файл не изменяется
